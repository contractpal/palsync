# Context-efficiency research

The implementation plan referred to six documentation sources and three papers without listing all
nine. This note uses the primary sources that directly govern PalSync's four hosts and cache model.

## Documentation

1. [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
   defines prefix matching over `tools`, `system`, then `messages`, with cache read/write usage
   reported separately. PalSync applies this by keeping generated bytes deterministic, placing no
   timestamps or live state in instructions, and distinguishing local stability from provider hits.

2. [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching) says Claude Code
   resends the system prompt, project context, conversation, and tool results each turn. PalSync
   therefore avoids rewriting unchanged project context and keeps large skill bodies on demand.

3. [Claude Code MCP and tool search](https://code.claude.com/docs/en/mcp) now documents deferred MCP
   tools as the default and caps individual tool descriptions/server instructions. This is newer
   than the plan's assumption that third-party deferral was unavailable. PalSync keeps one static
   schema for cross-host compatibility; it does not add host-specific dynamic profiles because
   Codex, Pi, and OpenCode do not document equivalent cache-preserving behavior.

4. [OpenAI prompt caching](https://platform.openai.com/docs/guides/prompt-caching) describes automatic
   reuse of the longest matching prompt prefix. PalSync can only make its contributed bytes stable;
   it cannot observe or claim OpenAI cache hits, so diagnostics say “locally stable prefix.”

5. [Codex manual](https://developers.openai.com/codex/codex-manual.md) documents `AGENTS.md` as
   automatically loaded durable repository guidance and `config.toml` as the MCP configuration
   surface. PalSync keeps Codex instructions in one managed `AGENTS.md` block and skill bodies in
   `.agents/skills` rather than duplicating them into the eager document.

6. [MCP lifecycle specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)
   includes optional server instructions in the initialize result, while the
   [MCP server-instructions guidance](https://blog.modelcontextprotocol.io/posts/2025-11-03-using-server-instructions/)
   warns that clients decide whether to surface them. Local verification found Pi's adapter lists
   tools but never reads instructions, so PalSync adds the shared preamble without removing the
   safety sentence from affected tool descriptions.

## Papers

1. [Prompt Cache: Modular Attention Reuse for Low-Latency Inference](https://arxiv.org/abs/2311.04934)
   shows the value of reusing shared prompt modules. PalSync's applicable lesson is structural:
   stable, separately hashed sections and on-demand bodies; it does not implement inference caching.

2. [Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks](https://arxiv.org/abs/2601.06007)
   reports that stable early content and dynamic content placed later outperform naïve full-context
   caching. PalSync applies exact deterministic generation and isolates the pal-specific sync tail.

3. [Cost-Efficient Serving of LLM Agents via Test-Time Plan Caching](https://arxiv.org/abs/2506.14852)
   proposes adapting cached plan templates for semantically similar requests. PalSync rejects this
   for spec-to-ship work: correctness depends on workspace/server state, and a local deterministic
   lint cache provides bounded reuse without substituting old plans for current reasoning.

## Decision

Optimize facts PalSync owns: byte determinism, stable ordering, semantic condensation, exact local
invalidation, and observability. Do not infer provider cache status, cache live server results, or
trade cross-host tool availability for a small schema reduction.
