- **The real fix: persist the transient pal id across sessions instead of re-deriving it every time — 2026-09-10**
  After the previous fix, David tested again and the SAME single "get status" call still showed one big block of `GetProfileList`/`GetGroupList`/`GetPalList` pairs before a final successful `GetPal`→`LockPal`→`GetPlatformInfo`. Diagnosis this time: that's not a repeat-walk bug — it's ONE walk (the necessary first-ever resolve of this pal in a brand-new session), which was always going to be expensive on an account with many profiles/groups, since there's no direct "look up by GUID" server endpoint. Every in-session caching fix so far only prevents *repeating* that walk within one session; a fresh session (a new pal tab, a new agent process) always paid it again from zero.
  David's key clarifying facts, verified directly against `lib/apiManager.js` rather than assumed: profileId/groupId are **never** sent on any actual per-pal action (`GetPal.do`, `LockPal.do`, `SavePal.do`, `CreateTunnel.do`, `GetPlatformInfo.do`, debug's `Ping.do` — all send `profileId: "-1"`, a placeholder) — they only matter for the three list/discovery endpoints used to *find* the pal. And critically: **the transient `palId` itself is not time-stamped or expiring** — safe to persist and reuse indefinitely, not just within one process's lifetime as the existing code comments assumed ("rotates per enumeration" means re-listing CAN hand back a different value, not that a previously-seen one goes stale).
  **Fix**: `.palsync.json` gets a new field, `palId` (`src/core/palsyncfile.js`) — the transient id itself, persisted after a successful resolve/lock (`src/launcher/workspace.js`'s initial setup, and `src/mcp/context.js`'s `buildContext` after every session's first `lifecycle.acquire()`). On the next session, `buildContext` seeds `lifecycle.lockState.resolved` from this persisted id BEFORE the first acquire — so that acquire goes straight to `GetPal.do` with a known-good id, skipping the account walk entirely, not even a cheap scoped one. Self-healing: `src/core/lock.js`'s `acquireByGuid` now validates a caller-supplied `resolved` against its own `GetPal.do` response (`success && pal` present) and transparently re-resolves for real (one full walk, then persists the fresh id) if it was ever actually stale — so a corrupted/rotted persisted id degrades to "pays the walk once more," never a hard failure.
  Net effect: only the very first-ever session against a pal (or a recovery after a genuinely stale id) pays the full walk; every session after that — even a brand-new process — starts with essentially the cheapest possible call.
  Verified via the full `npm test` suite, diffing failing-test-names before/after — zero new failures (the small residual noise is `test/snapshot.test.js`, a pre-existing timing-flaky suite confirmed to fail identically in isolation on a clean checkout, unrelated to file/identity-change tests this doesn't touch).
  **Confirmed live by David (2026-09-10) with a true cold restart** — closed and reopened a pal; the second session read the persisted `palId` from `.palsync.json` and skipped straight to the cheap path instead of re-walking the account.

- **Fixed: the real remaining chattiness — MCP tools that never used any cache at all, and the lock-at-open bug that made a fresh "get status" call read as unlocked — 2026-09-10**
  David tested after the lockLife.js/push.js fix (previous entry) with a single "get the status of this pal" — and it (a) reported the pal as "currently unlocked" even though it should have locked on open, and (b) still made hundreds of requests. Root causes, both in `src/mcp/tools.js`, not covered by the earlier fixes at all:
  1. **`pal_status` and `pal_resources` called `resolveServerPalByGuid` directly** — the full account walk — completely bypassing the ALREADY-EXISTING `resolvePalForRead(ctx)` cache helper (which some other tools already used). `pal_resources` explicitly "runs automatically at session start," so this fired the full walk unconditionally on nearly every session before the user did anything. Fixed: both now go through `resolvePalForRead(ctx)`.
  2. **`resolvePalForRead(ctx)` itself never wrote back to the cache on a miss** — so if it ran before anything else had populated `ctx.lifecycle.lockState.resolved`, it silently paid for the full walk EVERY time it was called, never actually caching anything for later callers (including itself). Fixed: it now writes the freshly-resolved pal into `ctx.lifecycle.lockState.resolved` on a miss — the same slot `lock.acquireByGuid` reads — so whichever tool resolves the pal first primes it for every other tool in the session, not just repeat calls to itself.
  3. **The lock was only acquired lazily, on the first tool call that actually needed one** (`src/mcp/server.js`'s `getCtx`) — a read-only-tagged tool like `pal_status`, if called FIRST, got a completely separate, deliberately-never-locking session (by design, for things like dataset reads that must never lock) instead of sharing the real one. Since nothing had triggered the real lock yet, `pal_status` correctly-but-misleadingly reported "unlocked" — no lock attempt had actually failed, none had been made. Fixed per David's explicit ask ("it should have been locked when I opened it"): `main()` now kicks off the real locked session immediately after server construction, not lazily — so by the time ANY tool runs, including a read-only one called first, it shares the one session that actually attempted the lock. A genuine denial (someone else holds it) still isn't an exception — it now surfaces via that shared session's real state to `pal_status`'s message or a write tool's own refusal, since MCP has no channel to pop an error before any tool is called.
  4. **`pal_pull` (`src/core/pull.js`) had the exact same never-cached direct resolve** — fixed the same way (accepts an optional `resolved`, `pal_pull`'s handler passes the cached one). Caught the same drift-marker-staleness risk as the earlier push.js fix while doing it: the returned marker now comes from this call's own always-fresh `GetPal.do` response, not the (possibly session-cached) `resolved.lastModifiedDate`.
  **Not yet touched**: `src/core/datasets.js`'s dataset query/sync functions and `src/core/merge.js` still call `resolveServerPalByGuid` directly with no cache passthrough — lower-traffic than status/resources/pull, left alone for now; worth the same fix if they're ever seen contributing to chattiness.
  Verified via the full `npm test` suite, diffing the exact set of failing test names (not just counts) before/after — zero new failures.

- **Fixed: the MCP session (and push specifically) was locking/unlocking on every single call, not just once per session — 2026-09-10**
  Follow-on from the resolve-walk fix below, after David asked "why so many GetPal/LockPal calls — is the agent constantly locking and unlocking with each post?" Answer: yes — `src/core/push.js` (backing `pal_push`, the single most-called tool in an active session) called `lock.acquireByGuid` completely fresh on **every push**, with no check for whether the session already held the lock. That call does `GetPal.do` (team-lock read) + `LockPal.do` (webstart-lock re-grant) + a best-effort `GetPlatformInfo.do` — every time, forever, regardless of the resolve-cache fix (which only ever addressed the `GetProfileList`/`GetGroupList`/`GetPalList` walk, not this).
  David's explicit design intent: **lock once when a pal is opened, unlock once when it's closed — no other lock/unlock requests during the session.**
  **Fix**: `src/core/lock.js`'s `acquireByGuid` now skips `LockPal.do` (and the `GetPlatformInfo.do` follow-up) entirely when `session.lockInfo.lockGranted` is already true — it just confirms with the (still-fresh-every-call) `GetPal.do` read from the team-lock check and returns immediately. Since the MCP server's `ctx` already does one real `lifecycle.acquire()` at session start (`buildContext`), and now `push()` accepts an optional cached `resolved` (wired from `ctx.lifecycle.lockState.resolved` in `src/mcp/tools.js`'s `pal_push` handler) to also skip the resolve walk, a push during an already-open session now makes exactly one call (`GetPal.do`) instead of the walk + `GetPal.do` + `LockPal.do` + `GetPlatformInfo.do`.
  **A real correctness risk caught along the way**: reusing a cached `resolved` across a whole session means `resolved.lastModifiedDate` (previously always freshly re-derived every push, since the walk happened every push) would go stale, and `push()`'s drift-guard compares exactly that field against the locally-tracked marker to detect a concurrent edit. Fixed by sourcing the drift marker from the ALWAYS-fresh `getPalResp` (still fetched every call) instead, falling back to the cached `resolved`'s value only if that's somehow absent. **Flagging**: this assumes `GetPal.do`'s response exposes `pal.lastModifiedDate` in the same shape `GetPalList.do`'s list entries do (same underlying server type) — a reasonable inference, not something I could verify live without hitting the real server; worth a quick confirm if drift detection is ever seen behaving oddly after this.
  Verified via the full `npm test` suite, comparing the exact set of failing test names (not just counts, which fluctuate from unrelated flaky tests) before/after — zero new failures.

## Fixed

- **console:start failures were completely silent — no error ever reached the user, for ANY cause — found on Mac 2026-09-10 (explicit OpenCode pick "doesn't work either")**
  After the picker fix above, David reported that explicitly picking OpenCode (not just leaving the default) still didn't start a console — which meant it wasn't the picker bug at all, since choosing an option does correctly set `agentId`. Traced it to something much broader: `gui/src/main/index.js`'s `console:start` handler called `ptyManager.start(...)` with no try/catch — a spawn failure there (e.g. `agent.command` not actually resolvable at exec time, even though the picker's own PATH check found it moments earlier) threw straight out of the IPC handler. On the renderer side, `ConsoleTab.jsx`'s call to `window.palsyncGui.startConsole(...)` was fire-and-forget — no `.then`/`.catch` at all — so **any** failure (a pty spawn error, or even the pre-existing "Could not register MCP" error path, which already returned `{error}` but nothing ever read it) resulted in the exact same silent blank terminal, for any underlying cause. Fixed: `index.js` now wraps the `ptyManager.start` call and returns a proper `{error}` on failure; `ConsoleTab.jsx` now awaits the result, shows the actual error message with a "Try a different agent" button (which re-opens the picker) instead of an unexplained black screen.
  This doesn't diagnose *why* OpenCode itself fails to launch on that Mac (missing from the actual exec PATH despite being found by the picker's `which` check, a broken shim, etc.) — but the next attempt will now show the real error text, which is what's needed to actually diagnose it. Not live-tested (would need a real OpenCode-launch failure to reproduce) — verified by code trace and a clean renderer build.

- **Multi-agent picker's "Open" button did nothing (black screen, no console started) — found on Mac 2026-09-10**
  Only shows up when more than one agent CLI is detected (Claude Code + OpenCode) — this Windows dev machine only ever had one on PATH, so the path was never exercised here until David hit it on his Mac. Root cause in `ConsoleTab.jsx`: the picker's `<select value={agentId || ""}>` has no empty option, so while `agentId` was still `null` (never seeded for the multi-agent case) the browser fell back to visually showing the first option ("Claude Code") as selected, while React's own `agentId` state stayed `null`. Clicking Open (without ever touching the dropdown, since it already looked correctly set) just dismissed the picker — the effect that actually starts the console never fired, since it required a truthy `agentId`. Fixed by seeding `agentId` to the first agent as soon as `agents` populates, even in the multi-agent case (keeping the visible selection and React state in sync from the start), and gating the console-start effect on `!needsAgentPick` too — otherwise seeding `agentId` immediately would have auto-started the console with the default agent before the user got to actually pick a different one from the dropdown.
  Not live-tested (no OpenCode install on this machine to reproduce the multi-agent path) — the fix is a straightforward controlled-input correctness fix, verified by full logic trace and a clean renderer build; worth a live confirm on the Mac machine where it was found.

- **Agent console permanently blank/black, zero output, zero error — found on Mac 2026-09-09 (David: "opens a pal, but there is nothing showing in the agent window")** — fixed
  Two compounding gaps. First, `ConsoleTab.jsx` seeded `agentId` straight from the pal's saved `agentId` (`pal.agentId`, persisted in the workspace JSON) without ever checking it against the currently-detected/installed agent list — only the *picker* path did that check. David's workspace had a pal saved with `agentId: "opencode"` from an earlier session; OpenCode was no longer (or never actually) on this Mac's PATH (confirmed: `which opencode` → not found, even under a full login shell). `ptyManager.start()` then called `pty.spawn("opencode", ...)`, which on macOS does **not** throw synchronously for a missing command the way the existing `console:start` try/catch (see the fix above) expected — it spawns, exits async with code 1, and writes nothing to the pty at all. Second, compounding it: `preload.js` already exposed `onConsoleExit`, but nothing in `ConsoleTab.jsx` ever called it, so even that async exit had no code path to surface it — a `console:start` call that returns `{ok:true}` (no throw) but whose process then dies immediately looked identical to one that was working fine, just silently, forever.
  Fixed both: (1) `ConsoleTab.jsx`'s agent-seeding effect now re-seeds (and shows the picker, if more than one agent is actually installed) whenever the current `agentId` isn't in the live `agents` list, not just when it's `null` — a stale saved agent no longer gets blind-trusted. (2) Wired up `onConsoleExit` in the terminal's mount effect to write an inline `[agent process exited with code N]` banner and reset `startedRef` so a retry can re-arm. Root cause verified by direct reproduction (spawning `claude`/`opencode` via the exact same `agentLaunch.ensureMcpRegistered` + `ptyManager.start` code path outside the GUI) and confirmed fixed by David after restarting the app.
  Follow-up, now also fixed (David asked specifically whether this would hold up on a packaged/signed Mac install — it wouldn't have): `ensureMcpRegistered()` used to skip re-running `register()` entirely once a pal's MCP config file (`.mcp.json`/`opencode.json`) already existed, so a config written during one launch never got its `command`/`args` corrected on the next — a real problem specifically for a packaged, unmoved (still-quarantined) `.app`, since macOS App Translocation gives Gatekeeper a *different* randomized temp path on every single launch (confirmed live in this workspace's `.mcp.json`, pointing at a since-vanished `AppTranslocation/.../Chip Pal Builder.app` path). `register()` is now called unconditionally every time — its own merge already replaces the `palsync` server entry wholesale (other configured servers untouched), so `ensureElectronRunAsNode`/`ensureChipSessionId` just re-apply on top as before. Verified live: re-running registration against this same pal rewrote the stale AppTranslocation path to the current binary's real path, and a second run produced no further diff (idempotent).
  Still not fixed, and harder: the equivalent drift in `.claude/settings.json` hook commands (`ensureElectronRunAsNodeForHooks`, same file). `claudeHooks.js` (the shared src/ module that already has a proper self-heal via `configure(workspaceDir, {install:true})`) recognizes a hook as "ours" only when its executable basename is a plain `node`/`node.exe` — never true for a hook written from inside Electron's main process (the executable is the Electron/app binary itself). Tried wiring `configure(install:true)` in here to reuse it; confirmed live that it does NOT recognize the GUI's existing (Electron-executable + `ELECTRON_RUN_AS_NODE=1`-prefixed) hook entries as owned, so instead of replacing them it appends a duplicate — which would grow by one more stale entry on every relaunch. Reverted. Actually fixing this needs `claudeHooks.js`'s own ownership detection taught about the Electron-wrapped form (both the current-process-exact-match check and `parseGeneratedCommand`'s hardcoded `{node, node.exe, nodejs, nodejs.exe}` executable set), not a workaround from the GUI side. Until then, a pal's Claude Code hooks (Stop/PreToolUse/PostToolUse) can go permanently stale after a packaged-app relaunch and need `.claude/settings.json` hand-fixed or the pal removed/re-added.

- **Windows build ballooned from ~193MB to 1.3GB+ after repeated rebuilds** — fixed
  Root cause: `gui/node_modules/palsync` (from `"palsync": "file:.."` in `gui/package.json`) is a Windows junction pointing at the entire repo root — `gui/node_modules/palsync/gui` **is** `gui/` itself, junction and all. Since `electron-builder`'s `files` allowlist doesn't restrict `node_modules/**`, every rebuild packaged the *previous* build's own output (a full `electron.exe` + Chromium, ~200MB+) sitting inside `gui/dist`, which was itself already packaged inside `gui/node_modules/palsync/gui/dist` — compounding on every rebuild. Fixed by adding `"!node_modules/palsync/gui/**"` and `"!node_modules/palsync/.git/**"` to `build.files` in `gui/package.json`. Confirmed fixed: installer back to 198MB, real `palsync` runtime code (`src/`, `bin/`, `bundled-context/`) still present in the asar. This almost certainly affects the Mac build the same way (same `file:..` mechanism) — make sure this fix is pulled before rebuilding there.

- **Version-check banner sends raw `process.platform` as `os=`** — confirmed no change needed
  `versionCheck.js` sends Node's raw values (`win32`/`darwin`/`linux`) to `getVersionInfo.do?ide=chip&os=<platform>`. David confirmed the endpoint is fine with these tokens as-is.

- **Claude Code hook commands written from inside the GUI relaunch the GUI instead of running palsync** — fixed (needs more real-world testing)
  Hooks written via `contextInject.js`/`claudeHooks.js` used `process.execPath` for the command's Node binary, which inside Electron's main process is `electron.exe`, not plain Node — same root cause `agentLaunch.js` already patched for MCP config, but that patch never covered hook commands. Fixed by a new `ensureElectronRunAsNodeForHooks(workspaceDir)` in `gui/src/main/agentLaunch.js`, which finds palsync-owned hook commands in `.claude/settings.json` and prefixes them with `set ELECTRON_RUN_AS_NODE=1 &&` (Windows) / `ELECTRON_RUN_AS_NODE=1 ` (POSIX), relying on the shell Claude Code already runs the command through. Wired into `ensureMcpRegistered()` (self-healing on every console launch) and `cloudWizard.js`'s `materialize()` (create-new/open-from-cloud path). Marked done per David; not yet confirmed against a live repeated-Stop-hook scenario — flag if it resurfaces.

- **Low-contrast text in Claude Code output** — fixed (GUI-side mitigation)
  Some chunks of Claude-generated code/text rendered as black-on-near-black, illegible — Claude Code's own ANSI color output likely assumes a light-background terminal theme, upstream of palsync's control. Mitigated in `ConsoleTab.jsx` by setting xterm.js's `minimumContrastRatio: 4.5`, which auto-adjusts a cell's foreground color to meet that contrast ratio against the terminal's background regardless of the color the CLI requested. Confirmed fixed by David.

- **Can't paste into the agent console input with Ctrl+V/Cmd+V** — fixed
  Confirmed: right-click paste worked, but keyboard paste didn't — xterm.js doesn't bind plain `Ctrl+V` to paste by default (it's a raw control byte a real terminal would send to the shell). Fixed in `ConsoleTab.jsx` by adding `term.attachCustomKeyEventHandler` to intercept Ctrl+V/Cmd+V, read `navigator.clipboard.readText()`, and call `term.paste(text)`.

- **Stale docs still tell the agent it can't create/edit a `datalist`** — fixed
  `bundled-context/skills/palbuilder-core/references/pal-json.md:127-130` said `data`/`datalists`/`dataviews` are "PalBuilder-provisioned... does not provision new ones via push... Create a new object in PalBuilder first" — stale for `data`/`datalists`, which are agent-editable via `pal_data_set`/`pal_data_delete` and `pal_datalist_set`/`pal_datalist_delete` (`src/mcp/tools.js:1836`, `:1873`; `src/core/dataObjects.js:120`, `:134`). Only `datasets`/`dataviews` still require PalBuilder. Reworded the summary paragraph to match what the detailed `data`/`datalists` sections already documented correctly.

- **New Workspace dialog closes when selecting the pre-filled name via mouse drag** — fixed
  In `LauncherView.jsx`, the "New Workspace" modal backdrop closed the dialog `onClick` (`gui/src/renderer/components/LauncherView.jsx:91`), so dragging to select the pre-filled name in the `<input>` (`:94`) and releasing outside the modal fired a `click` on the backdrop and closed the dialog. Fixed by closing on backdrop `onMouseDown` only when the mousedown target is the backdrop itself, so a drag that starts inside the modal no longer counts.

- **"Install" for Dependencies > Preview Browser (Chromium) launches a second GUI instance instead of just downloading** — fixed
  `installChromium()` in `gui/src/main/dependencyCheck.js:48` ran `spawn(process.execPath, [cli, "install", "chromium"])`. Under Electron, `process.execPath` is the Electron/app binary itself, not plain Node, so spawning it without `ELECTRON_RUN_AS_NODE=1` booted a second Electron app instance instead of running the Playwright CLI as Node. Fixed by passing `env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" }` to the `spawn()` call.
